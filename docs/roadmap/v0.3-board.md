# anvil v0.3 — Parity Execution Board

> **Premise.** v0.2 made anvil's perf advantage *felt* (95× build wall-clock,
> sub-2ms page loads). But the day-to-day operator surface still has gaps
> that block "anvil for our Java / Python / JS shop": no JUnit dashboard,
> no clickable file:line in errors, no PR-status integration, no matrix,
> no schedules, no secrets, no tool-version management. v0.3 closes those.
>
> **What v0.3 is NOT.** Not the leapfrog. Not flaky-test detection. Not
> SLSA provenance. Not remote build cache. Not container-as-step. Not AI
> authoring. Those are v0.4. v0.3 is **table stakes** — the features
> without which "yes, I'll switch from Jenkins/GHA to anvil" is structurally
> blocked.
>
> **Window.** 8 weeks. 1 week per major tranche, with T0 + T7 each ~half a
> week and T6 (secrets) ~1.5. Pile-Drive Mode applies — once a tranche is
> loaded, drive its PRs to merge.
>
> **Deploy posture (AV3-9, revised).** Public anvil deploy waits for the
> v0.3.0 ship. anvil's public debut should land with the seven parity
> features in place, not with visible gaps. v0.3 development happens
> against `lein run` locally and against the CI green from TR4. The
> deployment-gradient (private VPS → soft launch → full launch) starts
> the day T8 tags v0.3.0.

## Locked decisions (AV3-series)

These are not up for discussion mid-execution. If one needs to change,
stop the program, change the decision, restart.

| ID | Decision | Why |
|---|---|---|
| **AV3-1** | **Tier 1 only at v0.3.0.** Tier 2 leapfrog (flaky-test, SLSA, remote cache, container-as-step, AI authoring) defers to v0.4. | Discipline against scope creep. v0.3 must ship in 8 weeks; v0.4 has its own 10. |
| **AV3-2** | **JUnit XML (surefire-compatible) is the canonical test report format** at v0.3.0. xunit / cargo-json / jest-json parsers come in v0.3.1 if demanded. | Surefire is the lingua franca. It covers Java, JS (mocha-junit-reporter), Python (pytest `--junitxml`), Rust (cargo nextest `--junit`), .NET (vstest). |
| **AV3-3** | **GitHub Actions problem-matcher format** (`::warning file=…,line=…::msg`) is the wire format for clickable diagnostics. | Adopt the existing standard. Tools that emit it (LSPs, rustc, mypy) "just work." Don't invent a new format. |
| **AV3-4** | **GitHub status API for PR checks at v0.3.0.** GitLab MR + Bitbucket build status in v0.3.1. | 80% of OSS lives on GitHub. Ship the dominant case first. |
| **AV3-5** | **Matrix is declarative-only in v0.3.0.** No dynamic matrix from Groovy. | Match Jenkins's declarative `matrix { axes { axis { } } }`. Dynamic-matrix needs the scripted-Pipeline runtime — separate scope. |
| **AV3-6** | **Secrets file-encrypted at rest** (AES-256-GCM via `javax.crypto`); master key from env-var or local file. No Vault / Cloud-KMS integration in v0.3.0. | Cover the 95% case (solo / small-team self-host). Vault and cloud KMS backends in v0.3.x as plug-ins. |
| **AV3-7** | **`mise` as primary tool-version backend; `asdf` detected as fallback.** Project's `.tool-versions` / `.mise.toml` auto-detected pre-build. | mise is the 2026 standard (asdf successor with shared file format). Fallback covers existing asdf shops. |
| **AV3-8** | **Cron expressions only at v0.3.0** (no schedule-UI builder). `triggers { cron('@daily') }` Jenkins-compat syntax + `H` (hash-based) slots. | Match Jenkins. Schedule UI builder in v0.4 alongside AI authoring. |
| **AV3-9** | **Public anvil deploy waits for v0.3.0 ship.** First public impression must include the seven Tier-1 features; deploying v0.2 publicly would invite "but does it have JUnit / matrix / secrets?" → game over. Revised 2026-06-03 (was: deploy-first, then build features). | First impression dominates. Anvil's debut should lead with parity + the 95× perf story, not with visible gaps. Strategic / marketing call overrides engineering-shaped "deploy validates first" logic, because anvil has months of internal use already (TU0–TU6 receipts). |
| **AV3-10** | **All v0.3 features land on `superbadlabs/anvil/master` via PR + green CI.** `--admin` only with a documented org-policy edge case. | Sustainable for collaborators; honors the branch-protection investment from TR4. |

## Scope guardrails

| IN (v0.3.0) | OUT (deferred to v0.4 or later) |
|---|---|
| JUnit / surefire XML parser + storage + UI dashboard | Flaky-test detection (passed-on-retry analysis) |
| Problem-matcher (GHA format) regex rules library | SLSA L3 provenance signing |
| PR-check integration via GitHub status API | Remote build cache (content-addressed step caching) |
| Declarative matrix builds (axes, exclusions) | Container-as-step (`steps { container 'maven:…' { sh '…' } }`) |
| Scheduled triggers (cron) | AI pipeline authoring (`anvil init`, `anvil explain`, `anvil optimize`) |
| Secrets management (file-encrypted, masked in logs, env-injected) | Cost / minute reporting |
| `mise` / `asdf` tool-version detection | GitLab MR + Bitbucket PR-check support (deferred to v0.3.1) |
| Hop release tag: **`v0.3.0`** | xunit / cargo-json / jest-json test parsers (v0.3.1) |
| New SSE event types: `:test-completed`, `:checks-updated`, `:schedule-fired`, `:secret-rotated` | Dynamic matrix from Groovy (needs scripted-runtime polish) |
| Docs: one .md per feature under `docs/{junit,problem-matchers,pr-checks,matrix,scheduler,secrets,tools}/` | Vault / Cloud-KMS secret backends (v0.3.x) |

If you find yourself in the OUT column mid-tranche, file an issue, link
the AV3 decision, and back out.

## Risk register

| ID | Risk | Mitigation |
|---|---|---|
| **R1** | Surefire XML has 4+ dialects (TestNG, JUnit 4, JUnit 5, Maven Surefire 2.x vs 3.x). Parser fragility. | Parse the common subset first (`<testsuite>` + `<testcase>` with `<failure>`/`<error>`/`<skipped>`); document unsupported dialects; ship 4 golden corpus samples in tests |
| **R2** | Problem-matcher regex library bloat — every tool wants its own rule | Ship core set (gcc, rustc, mypy, eslint, javac, msbuild) hand-tuned; community contrib via YAML data files, never code |
| **R3** | GitHub PR-check API needs a GitHub App or PAT; auth setup is friction | Document both paths; ship `docs/pr-checks/github-app-setup.md` + `pat-setup.md` + curl diagnostic |
| **R4** | Matrix expansion explodes on misconfigured axes (`N × M × K` blows up) | Cap matrix size at 100 cells by default; configurable via `:anvil.matrix/max-cells`. Fail fast with a clear error message. |
| **R5** | Cron scheduler clock drift in long-running anvil instance | Use `java.time.ZonedDateTime` consistently; document timezone (default UTC, override via `:anvil.scheduler/timezone`) |
| **R6** | Secrets — master-key rotation story is hard | v0.3.0 ships with `anvil secrets rotate-master --new-key …` (one-shot decrypt with old + re-encrypt with new). Automated rotation deferred to v0.3.x |
| **R7** | `mise` integration depends on `mise` being installed on PATH; not present on default Ubuntu / Mac | `anvil setup tools` CLI installs mise via the official one-liner if absent; doc the asdf-fallback path |
| **R8** | New SSE event types might bloat the bus → memory pressure | TU1.7's 100-session soak proved the bus scales; each new event topic adds ≤1% per topic per existing measurement. Re-bench in T0.3 |
| **R9** | UI dashboard widgets (test trends, problems tab, matrix grid) grow page weight | Hold pages under their TU0.7 budgets (p50 < 50 ms). Re-bench in T8.2. Reject UI work that breaches budget without a clear amortizing benefit |
| **R10** | v0.3 features land on extracted anvil, exposing untested edges from the extraction itself | T0 baseline + T8 cross-feature smoke surface this; any extraction-shaped issues feed back as anvil 0.2.x patches |

### T1 — JUnit / surefire test reporting (1 week)

**Goal**: Builds that produce JUnit XML reports get a per-build test-results dashboard: pass/fail counts, failed-test list with stack traces, sortable by duration, sparkline of pass rate across last 30 builds.

**Depends on**: T0
**Exit criteria**: a Java build emitting surefire XML at `target/surefire-reports/*.xml` shows a populated test-results panel on the build page with clickable failed-test stacktraces

- [ ] **T1.1** — `anvil.compat.junit/parse-xml` — surefire XML parser. Emits `[:test/result {:test-id, :name, :class, :status, :duration-ms, :failure-msg, :failure-trace}]`. Tolerate TestNG, JUnit 4, JUnit 5, Maven Surefire 2.x and 3.x quirks (common subset only).
- [ ] **T1.2** — `anvil.compat.junit/scan-build-artifacts` — after build completes, scan workspace for `target/surefire-reports/*.xml` (configurable glob); parse + persist.
- [ ] **T1.3** — DB schema: `test_results` table with FK to build, indexed on `(job-id, test-id)` for trend queries. Migration as Chengis-style migration file.
- [ ] **T1.4** — `anvil.web.views.test-results` — Hiccup view: summary card, failed-test list with collapsible stacks, sortable-by-duration table, 30-build sparkline of pass rate. SVG for the sparkline (matches TU3.6 pattern).
- [ ] **T1.5** — SSE event: `:test-completed` published after T1.2 finishes; widget on build page swaps from "(scanning…)" placeholder live.
- [ ] **T1.6** — Jenkinsfile compat: `junit 'target/surefire-reports/*.xml'` step → routes to T1.2 directly. Sample project receipt at `benchmarks/results/v0.3-junit-receipt.md`.
- [ ] **T1.7** — Tests: 4 surefire XML samples (TestNG, JUnit 4, JUnit 5, Maven Surefire 3.x), all parse to consistent IR. Browser test for the dashboard view.

**Depends on**: T0

- [ ] **T2.4** — `anvil.web.views.problems` — Hiccup view: severity-filtered list, clickable file:line that opens a source preview (read file from workspace if available).

- [ ] **T2.7** — Tests: golden corpus of 8 tool outputs → expected `problems` ledger. Browser test for clickable file:line.

### T3 — PR-check integration (GitHub status API) (1 week)

**Goal**: anvil reports build status back to GitHub PRs. A PR view on github.com shows anvil's check with green/red status, build duration, link to the build page. Re-run from PR updates status.

**Depends on**: T0
**Exit criteria**: opening a PR on a configured repo triggers an anvil build; the PR's "Checks" section shows "anvil — <status>"; clicking lands on the build page; manually re-running from PR updates status

- [ ] **T3.1** — `anvil.integration.github/auth` — accept either GitHub App credentials (preferred) or PAT (fallback). Tokens stored as secrets (forward dep on T6; mock for T3 dev, real wiring on T6 merge).
- [ ] **T3.2** — `anvil.integration.github/checks-api` — POST/PATCH `https://api.github.com/repos/{owner}/{repo}/check-runs` to create/update a check on a SHA. Handles in_progress, success, failure, neutral, cancelled.
- [ ] **T3.3** — Webhook receiver: `POST /anvil/webhooks/github` for `pull_request` events. Maps PR to a job (job's repo URL match) and triggers a build with the PR's SHA. Publishes `:checks-updated` on the bus.
- [ ] **T3.4** — Build lifecycle hook: on `:build-started` → checks-api "in_progress"; on `:build-done` → checks-api success/failure with summary (duration + test count from T1 if test job).
- [ ] **T3.5** — Per-job config: `:anvil.github/checks-enabled?`, `:anvil.github/repo`, `:anvil.github/installation-id` (for App auth).
- [ ] **T3.6** — Build page UI: "Posted to github.com/.../checks/123" pill linking to the PR. Re-run button hits the same checks-api PATCH.
- [ ] **T3.7** — Docs: `docs/pr-checks/github-app-setup.md`, `docs/pr-checks/pat-setup.md`, `docs/pr-checks/diagnostic.md` (curl-based).

### T4 — Declarative matrix builds (1 week)

**Goal**: A Jenkinsfile that declares a matrix builds N parallel jobs cross-producting all axes. The build page shows a matrix grid with per-cell status.

**Depends on**: T0
**Exit criteria**: a Jenkinsfile with `matrix { axes { axis { name 'JDK'; values 17,21 } axis { name 'OS'; values 'linux','windows' } } stages { … } }` produces 4 cell-builds whose statuses appear on a single build page in a 2×2 grid

- [ ] **T4.1** — `anvil.compat.jenkins.matrix-parser` — extend Jenkinsfile parser to handle `matrix { axes { } excludes { } stages { } }` blocks. Produces a matrix-IR with per-axis values + exclusion patterns.
- [ ] **T4.2** — `anvil.compat.jenkins.matrix-expander` — at build-trigger time, cross-product axes, apply excludes, produce N child build specs. Each child is a normal anvil build with its axis values injected as env (`JDK=17`, `OS=linux`).
- [ ] **T4.3** — DB schema: extend `builds` table with `parent_build_id` and `matrix_axes` (JSON of axis values for this cell). Migration file.
- [ ] **T4.4** — Dispatcher concurrency: matrix children run subject to `:max-concurrent-builds` of the job; queue ordering visible on the parent build page.
- [ ] **T4.5** — `anvil.web.views.matrix` — Hiccup grid view: rows × columns = first 2 axes; cells link to child builds; SSE-live as cells complete.
- [ ] **T4.6** — SSE: existing `:build-done` event flows up to a parent matrix-update widget → grid cells light up live.
- [ ] **T4.7** — Per-job config: matrix size cap (`:anvil.matrix/max-cells` default 100, fail-fast above with a clear error).
- [ ] **T4.8** — Tests: 3 Jenkinsfile matrix samples (2-axis simple, 3-axis with excludes, 1-axis edge case) → expected cell-builds. Browser test for grid view.

### T5 — Scheduled triggers (cron) (1 week)

**Goal**: A Jenkinsfile with `triggers { cron('@daily') }` runs the job nightly without manual trigger. The job page shows "Next run: …".

**Depends on**: T0
**Exit criteria**: a job with `cron('@hourly')` triggers a build every hour with `:trigger :scheduled` in the build metadata; the job page surfaces "Next run: T+57 min" live

- [ ] **T5.1** — `anvil.scheduler.cron-parser` — parse Jenkins cron syntax (`@daily`, `@hourly`, `@weekly`, `0 6 * * *`, and `H H * * *` where `H` = hash of job name into the slot — Jenkins's H-system for spreading load).
- [ ] **T5.2** — `anvil.scheduler.engine` — single Java scheduler thread; on init, for each job with a cron trigger, register next-fire time; on fire, trigger a build with `:trigger :scheduled :triggered-at <inst>`.
- [ ] **T5.3** — Bus event: `:schedule-fired {job, next-run}` after each cron fire; widget on the job page updates.
- [ ] **T5.4** — Jenkinsfile compat: `triggers { cron('@daily') }` → routes to T5.1/T5.2.
- [ ] **T5.5** — UI: "Next scheduled run: …" pill on job page. Live updates via T5.3 event.
- [ ] **T5.6** — Config: `:anvil.scheduler/timezone` (default `UTC`).
- [ ] **T5.7** — Tests: cron parser golden corpus (15 expressions); scheduler unit test with mocked clock; verify `:trigger :scheduled` metadata in the build record.

### T6 — Secrets management (~ 1.5 weeks)

**Goal**: `withCredentials([usernamePassword(credentialsId: 'docker-hub', usernameVariable: 'USER', passwordVariable: 'PSW')])` works on anvil. Secrets are encrypted at rest, env-injected at build time, masked in logs.

**Depends on**: T0
**Exit criteria**: admin creates a secret via `anvil secrets add`; Jenkinsfile referencing `credentialsId: 'foo'` reads it as env vars during the wrapped block; the secret value never appears in build logs (replaced with `***`)

- [ ] **T6.1** — `anvil.secrets.crypto` — AES-256-GCM via `javax.crypto`; master key from `ANVIL_SECRETS_KEY` env-var (32 random bytes, base64). Encrypted blob = `nonce ++ ciphertext ++ auth-tag`.
- [ ] **T6.2** — DB schema: `secrets` table (`id`, `name`, `type`, `encrypted_value`, `created_at`, `last_used_at`).
- [ ] **T6.3** — CLI: `anvil secrets {add,list,rotate,delete}`. Read secret value from stdin only (never argv — `ps` would leak it). Print preview hash, not value.
- [ ] **T6.4** — `withCredentials` step impl: decrypt + inject as env (`FOO_USR`/`FOO_PSW` for username-password, `FOO` for string, file path for file). Decryption happens in the dispatcher per build; secrets never touch disk in cleartext.
- [ ] **T6.5** — Log masking: every secret value added to a per-build "redaction set"; the log streamer replaces any occurrence with `***` *before* publishing to the bus (so SSE viewers also see the redaction).
- [ ] **T6.6** — UI: secrets list page (admin-only, gated by future RBAC — for v0.3 single-tenant, by trusted-IP middleware). Names + types + last-used. Add/rotate flow from UI uses the same CLI codepath.
- [ ] **T6.7** — Rotation: `anvil secrets rotate-master --new-key <new-32-bytes>` — one-shot decrypt with old key + re-encrypt with new. Old key required.
- [ ] **T6.8** — Docs: `docs/secrets/operator-guide.md` (master key setup, env-var vs file backend, rotation procedure), `docs/secrets/threat-model.md` (what we protect against vs not — esp. NOT protecting against compromised anvil process).
- [ ] **T6.9** — Tests: encrypt/decrypt round-trip; redaction over 5 log shapes (multi-line, embedded in JSON, partial match); CLI smoke; Jenkinsfile `withCredentials` compat sample.

### T7 — mise / asdf tool-version detection (~ half week)

**Goal**: A repo with a `.tool-versions` or `.mise.toml` file gets its declared tool versions provisioned before build steps run. Build logs show `using mise: nodejs 22.5.1, python 3.12.7, …`.

**Depends on**: T0
**Exit criteria**: a build on a project with `.tool-versions` (`nodejs 22.5.1`, `python 3.12.7`) auto-provisions both via mise (if available); `node --version` / `python --version` in subsequent `sh` steps report the declared versions

- [ ] **T7.1** — `anvil.tools.mise/detect` — look in workspace for `.mise.toml`, `mise.toml`, `.tool-versions`. Return declared tools.
- [ ] **T7.2** — `anvil.tools.mise/provision` — if `mise` on PATH, run `mise install` in workspace; else if `asdf` on PATH, use `asdf install`; else log warning + continue.
- [ ] **T7.3** — Dispatcher hook: before first `sh` step, run T7.2; results show in console as a fold-able stage.
- [ ] **T7.4** — CLI: `anvil setup tools` — installs mise via the official one-liner if absent. Doc the asdf-fallback path.
- [ ] **T7.5** — Tests: 3 project samples (`.tool-versions` only; `.mise.toml` only; both). Smoke test the provision path with a fake `mise` shim binary.

## Anti-goals (resist)

- **Do not start v0.4 features in v0.3.** Discipline against scope creep (AV3-1).
- **Do not invent a new problem-matcher format.** Adopt GHA's (AV3-3).
